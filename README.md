Монорепозиторий прототипа AI-buddy — ИИ-наставника для стажёров (кейс Avito Start, Hack&Change 2026). Документ описывает назначение каждой папки, ключевые архитектурные решения и зоны ответственности в команде.

## Общая схема

```
React-чат + панель прогресса
        │                    │
        │ чат                │ прогресс, заявки, логин (REST, без LLM)
        ▼                    ▼
     agent/              backend/cmd/api
  (LLM + цикл tools)         │
        │ MCP + токен        │
        ▼                    │
  MCP-серверы на Go ─────────┤
  ├── mcp-docs        search_docs (RAG)
  ├── mcp-onboarding  задачи, статусы, следующий шаг
  ├── mcp-absences    заявка на отгул (имитация сервиса)
  └── mcp-access      заявка на доступ (имитация сервиса)
        │
        ▼
   PostgreSQL + pgvector
```

## Корень проекта

| Файл | Назначение |
|---|---|
| `README.md` | Инструкция запуска через Docker, версии зависимостей, тестовые учётки, порядок проверки сценариев, запуск тестов и отчёт о покрытии. Без рабочей инструкции решение не проходит допуск. |
| `docker-compose.yml` | Все сервисы проекта: Postgres, MCP-серверы, `api`, агент, фронтенд. Цель — запуск одной командой `docker compose up`, включая загрузку базы знаний. |
| `.env.example` | Шаблон переменных окружения без секретов: адреса сервисов, названия моделей, место под ключ API. Настоящий `.env` в репозиторий не попадает. |
| `.gitignore` | Исключения: `.env`, бинари, отчёты о покрытии, `node_modules`. |
| `Makefile` | Короткие команды для частых действий: `make up`, `make ingest`, `make test`, `make coverage`. |

| Путь | Назначение |
|---|---|
| `knowledge/` | База знаний в markdown — источник для RAG. |

## `backend/` — весь Go-код

Один Go-модуль: общий `go.mod`, общие пакеты, несколько программ.

| Путь | Назначение |
|---|---|
| `go.mod` | Модуль и зависимости: MCP SDK, pgx, pgvector и другие. |
| `Dockerfile` | Multi-stage сборка: в первой стадии собираются все бинари из `cmd/`, во второй остаётся лёгкий образ. В `docker-compose.yml` каждый сервис запускает свой бинарь из этого образа. |
| `migrations/` | SQL-миграции: пользователи, роли, задачи, заявки, чанки с векторами, индексы. Применяются через golang-migrate при старте. |

### `backend/cmd/` — точки входа

Каждая подпапка — отдельная программа со своим `main.go`. В `main` только сборка зависимостей и запуск: конфиг → подключение к базе → создание сервисов → регистрация хендлеров → старт сервера. Бизнес-логики здесь нет.

| Путь | Назначение |
|---|---|
| `api/` | REST-сервер для фронтенда: логин по тестовой учётке с выдачей JWT, данные панели прогресса, история заявок. Работает без LLM, чтобы локальные операции укладывались в 1 секунду. |
| `ingest/` | Консольная утилита: читает `data/knowledge`, режет документы на чанки, считает эмбеддинги, записывает в pgvector. Запускается при первом старте или после изменения документов и завершается. |
| `mcp-docs/` | MCP-сервер с tool `search_docs`: поиск фрагментов по базе знаний с учётом команды пользователя. |
| `mcp-onboarding/` | MCP-сервер чек-листа адаптации: задачи пользователя, следующий шаг, смена статуса задачи. |
| `mcp-absences/` | Имитация сервиса отсутствий: создание заявки на отгул и получение её статуса. Основное «действие через корпоративный сервис». |
| `mcp-access/` | Имитация сервиса доступов (дополнительный сценарий). |

### `backend/internal/` — общий код и домены

Пакеты внутри `internal` нельзя импортировать из других модулей — это ограничение компилятора Go, гарантирующее, что код используется только внутри проекта.

**Общие пакеты**

| Пакет | Назначение |
|---|---|
| `config/` | Чтение настроек из переменных окружения со значениями по умолчанию. Один тип конфига для всех бинарей. |
| `auth/` | Выпуск JWT (в `api`) и проверка (в MCP-серверах). Функции «положить пользователя в контекст» и «достать пользователя из контекста» для проверки прав в сервисах. |
| `postgres/` | Создание пула соединений pgx и хелпер для транзакций. |
| `mcpserver/` | Общая обвязка MCP-серверов: HTTP-сервер, middleware с проверкой токена, `/healthz`, логирование, graceful shutdown. Новый MCP-сервер — это несколько строк в `main.go`, а не копия существующего. |
| `events/` | Запись событий для метрик: вопрос задан, ответ найден или нет, действие выполнено, задача отмечена. |
| `rag/` | Чанкер, клиент эмбеддингов, запросы к pgvector. Используется в `ingest` (запись) и в `mcp-docs` (поиск). |

**Доменные пакеты** `onboarding/`, `absences/`, `access/` устроены одинаково:

| Файл | Назначение |
|---|---|
| `model.go` | Типы предметной области (этап, задача, статус, заявка) и допустимые значения. Без зависимостей от базы и HTTP. |
| `repository.go` | Интерфейс хранилища: какие операции с данными нужны сервису. Только сигнатуры. |
| `postgres.go` | Реализация интерфейса на pgx: конкретные SQL-запросы. |
| `service.go` | Бизнес-логика и проверка прав пользователя. Зависит от интерфейса репозитория, поэтому тестируется с фейковым хранилищем. Основной объём тестов для покрытия > 80%. |
| `mcp.go` | Tool-хендлеры для агента: разбор входа, вызов сервиса, понятный модели текст результата. |
| `http.go` | REST-хендлеры для фронтенда поверх того же сервиса. |

## `agent/` — диалоговый сервис

Принимает сообщения пользователя из фронтенда, отправляет их модели вместе со списком tools, вызывает MCP-серверы и возвращает ответ. Внутри: клиент LLM, цикл агента с лимитом шагов, системный промпт, MCP-клиент с передачей токена пользователя, история диалога, отдача статуса ожидания во фронтенд.

Генерационная часть RAG находится здесь: агент получает от `search_docs` найденные фрагменты и формулирует ответ со ссылками на источники. Модель эмбеддингов агенту не нужна — она используется только в `backend`.

## `frontend/` — интерфейс

React + TypeScript.

| Путь | Назначение |
|---|---|
| `src/api/` | Клиенты к агенту (чат) и к `api` (логин, прогресс, заявки). Компоненты не обращаются к сети напрямую. |
| `src/components/Chat/` | Окно диалога: сообщения, ввод, индикатор ожидания, понятная ошибка при сбое модели или сервиса. |
| `src/components/ProgressPanel/` | Панель рядом с чатом: этапы адаптации, задачи со статусами, следующий шаг. |
| `src/components/RequestCard/` | Карточка заявки: собранные данные, подтверждение перед отправкой, итоговый статус. |
| `src/pages/` | Страницы: вход под тестовой учёткой и основной экран. |
| `src/store/` | Состояние приложения: пользователь, история чата, прогресс. |

## Ключевые решения

1. **Пакеты по фичам, а не по слоям.** Код одного домена лежит в одном пакете со всеми слоями. Домены не зависят друг от друга, а работа делится между участниками без конфликтов.
2. **Одно ядро, два входа.** `mcp.go` и `http.go` — тонкие адаптеры над одним `service.go`. Агент и панель прогресса всегда показывают одинаковые данные.
3. **Панель прогресса работает без LLM.** Фронтенд получает статусы напрямую из `api`. Через агента идут только диалоговые сценарии, поэтому простые операции укладываются в 1 секунду.
4. **Права проверяются в сервисах, а не в промпте.** Агент передаёт токен пользователя в MCP-серверы, middleware кладёт пользователя в контекст, сервис проверяет доступ. Инструкция модели не является защитой; сервис просто не возвращает недоступные данные.
5. **Каждый корпоративный сервис — отдельный MCP-сервер.** Имитация заменяется настоящим API без изменения агента. Все бинари собираются одним образом. Допустим компромисс из двух серверов: `mcp-buddy` (база знаний и чек-лист) и `mcp-corporate` (имитации внешних сервисов). Структура `internal/` при этом не меняется.
6. **Имена tools уникальны во всех серверах.** Агент объединяет списки tools, поэтому имена говорящие: `get_absence_status`, `get_task_status`.
7. **База знаний разложена по командам.** Метка команды у документа позволяет учитывать контекст пользователя при поиске.
8. **Одна база PostgreSQL.** pgvector для RAG и обычные таблицы для задач и заявок. Redis в MVP не используется; возможное применение — кэш сессий и истории диалогов.

## Зоны ответственности

| Папки | Ответственный |
|---|---|
| `backend/`, `data/`, `docker-compose.yml` | backend |
| `agent/` | AI/агент |
| `frontend/` | frontend |
| `docs/specs/`, `docs/metrics.md`, `README.md` | вся команда, с назначенным ответственным |

Граница между backend и агентом проходит по протоколу MCP: агенту нужны только адреса серверов, список tools и способ передачи токена пользователя.
