# 03. Отгул через имитацию HR-системы

Код: `backend/internal/absences/` (`model.go`, `service.go`, `mcp.go`, `http.go`), `backend/cmd/mcp-corporate/main.go`, миграции `0005_requests.up.sql`, `0007_demo_data.up.sql` и `0009_time_off_reason.up.sql`, политика вызова в `agent/src/clients/tools.py`.
Тесты: `backend/internal/absences/service_test.go`, `backend/internal/absences/handlers_test.go`, `backend/cmd/mcp-corporate/main_test.go`, `agent/tests/test_chat.py::test_time_off_identity_and_key_are_supplied_by_code`, `agent/tests/test_mcp_routing.py`.
Подробности о причине и обнаружении инструментов: [docs/mcp-discovery.md](../mcp-discovery.md), [docs/time-off.md](../time-off.md).

## Цель

Стажёр не знает, как оформить отгул, и не хочет отвлекать руководителя. Buddy объясняет порядок и по явной просьбе создаёт заявку в корпоративном сервисе отсутствий (в прототипе это имитация). Результат, номер и статус заявки, Buddy показывает и сохраняет. Это сценарий с действием через корпоративный сервис, которого требует кейс.

## Пользовательские истории

- «Как оформить отгул?» Buddy объясняет порядок и ничего не создаёт.
- «Оформи мне отгул.» Buddy уточняет дату.
- «Оформи отгул на 20 ноября.» Buddy спрашивает причину и пока ничего не создаёт.
- «По семейным обстоятельствам.» Buddy создаёт заявку на один день с датой из прошлого сообщения и отвечает номером и статусом «подана».
- «Оформи отгул с 1 по 3 декабря, причина: экзамен.» Заявка на три дня сразу: дата и причина уже названы.
- «Покажи мои заявки.» Список последних заявок со статусами.

## Почему отдельный MCP-сервер

Инструменты заявок отдаёт отдельный сервер `mcp-corporate`, а не `mcp-buddy`. Это имитация корпоративной HR-системы: чтобы подключить настоящий сервис отсутствий Авито, достаточно заменить этот сервер адаптером с теми же именами инструментов. Агент и промпт при этом не меняются, меняется только `MCP_CORPORATE_URL`. Агент получает инструменты и их схемы от сервера через `tools/list`, поэтому новый тип заявки (командировка, доступ) на этом сервере становится доступен модели без правки кода агента.

## Поведение агента

1. Перед оформлением агент вызывает `get_request_types` и узнаёт обязательные поля.
2. На вопрос «как оформить» агент только объясняет порядок.
3. Заявка создаётся только по явной просьбе оформить и только при известной дате начала. Даты агент не выдумывает; неоднозначную дату уточняет.
4. Одна названная дата означает отгул на один день: дату окончания агент не переспрашивает.
5. **Причина обязательна.** Если пользователь её не назвал, агент спрашивает причину и не создаёт заявку. В `reason` передаётся дословный фрагмент слов пользователя. Код агента сверяет причину с сообщениями пользователя в доступной истории; если её там нет или она пустая, сервер не вызывается, а модель получает просьбу уточнить причину. Если старая часть истории была сокращена, агент попросит повторить причину.
6. Ключ повтора `time-off:<run_id>` подставляет код агента, модель его не выбирает. Пользователь определяется по токену, а не по аргументам модели.
7. Об успехе агент говорит только после результата с `id` и `status`. `submitted` означает «заявка подана», а не «согласована».
8. При ошибке агент объясняет её смысл. При неизвестном исходе сначала проверяет `list_my_requests`, а потом повторяет.
9. Агент не обещает уведомить наставника: уведомлений в прототипе нет.

## Правила заявки `time_off`

| Поле | Правило |
|---|---|
| `start_date` | обязательно, `YYYY-MM-DD`, не раньше сегодняшней даты по Москве |
| `end_date` | необязательно; пусто означает один день (`end_date = start_date`); не раньше начала |
| длительность | не больше 30 дней включительно |
| `reason` | обязательно, непустое после обрезки пробелов, до 2000 символов (миграция `0009` делает поле обязательным в шаблоне типа) |
| `idempotency_key` | обязательно, 1–200 символов |

Повтор с тем же ключом и теми же данными возвращает исходную заявку, даже если её даты уже прошли. Тот же ключ с другими данными даёт конфликт. Вторая активная заявка (`submitted` или `approved`) на точно такой же диапазон дат запрещена, даже из другого чата. Частично пересекающиеся диапазоны пока допускаются.

Статусы заявки: `submitted`, `approved`, `rejected`, `cancelled`. В прототипе создаётся только `submitted`, согласования нет.

## Инструменты (MCP, сервер `mcp-corporate`)

| Инструмент | Вход | Выход |
|---|---|---|
| `get_request_types` | `{}` | `{ "types": [ { "code": "time_off", "title": "Отгул", "description": "…", "fields": { … } } ] }` |
| `list_my_requests` | `{}` | `{ "requests": [ Request ] }`, последние 100 своих заявок |
| `create_time_off_request` | `{ "start_date", "end_date"?, "reason", "idempotency_key" }`; модель `idempotency_key` не видит | `Request` |

`Request`:
```json
{ "id": 7, "type_code": "time_off",
  "data": { "start_date": "2026-11-20", "end_date": "2026-11-20", "reason": "семейные дела" },
  "status": "submitted", "created_at": "2026-11-14T10:00:00Z" }
```

Ошибки ввода и конфликта модель получает текстом, например «укажите причину отгула», «даты YYYY-MM-DD, начало не раньше сегодня (Москва), конец не раньше начала» или «заявка на эти даты уже существует; посмотри список заявок». Сбои базы скрываются за «request service unavailable».

## REST для интерфейса

Все ручки за `requireAuth`.

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/request-types` | доступные типы и поля |
| GET | `/api/requests` | последние 100 своих заявок |
| POST | `/api/requests/time-off` | тело `{start_date, end_date?, reason, idempotency_key}`; 200 `Request`; 400 неверный JSON; 401 без токена; 422 неверные данные; 409 конфликт |

## Права и данные

- Автор заявки всегда пользователь из токена; список заявок фильтруется по нему.
- Тип заявки берётся из `buddy.request_types` только если он включён (`enabled`).
- Персональные данные не запрашиваются: только даты и причина своими словами. Финансовых операций нет.
- Старые заявки без причины остаются доступны; повтор старой заявки с тем же ключом работает как раньше.

## Критерии приёмки

| Критерий | Тест |
|---|---|
| Даты и причина проверяются: формат, не в прошлом по Москве, конец не раньше начала, не больше 30 дней; пустая или из пробелов причина отклоняется, длиннее 2000 символов тоже | `service_test.go::TestValidation`, `TestValidationUsesMoscowDate` |
| Одна дата даёт отгул на один день | `service_test.go::TestCreateOneDayDefaultsEndDate` |
| Повтор возвращает исходную заявку, другой payload с тем же ключом даёт конфликт, дубль дат даёт конфликт | `service_test.go::TestCreate` |
| Типы и список заявок читаются только свои и только включённые | `service_test.go::TestTypes`, `TestList` |
| REST и MCP отдают одинаковые данные и коды ошибок, сбои базы скрыты | `handlers_test.go::TestHTTP`, `TestMCP` |
| Пользователь и ключ повтора подставляются кодом агента, не моделью | `agent/tests/test_chat.py::test_time_off_identity_and_key_are_supplied_by_code` |
| Без причины сервер не вызывается, ключ повтора скрыт от модели | `agent/tests/test_mcp_routing.py::test_missing_reason_never_calls_server_and_key_is_hidden` |
| Инструменты вызываются на тот сервер, с которого получены | `agent/tests/test_mcp_routing.py::test_new_tool_uses_discovered_schema_and_server`, `test_direct_call_discovers_route` |
| Диалог «Оформи отгул на 20 ноября» → вопрос о причине → «По семейным обстоятельствам» создаёт заявку и показывает номер и статус | Вручную, сценарий 3 в [README](../../README.md#порядок-проверки) |

## Вне рамок

- Согласование руководителем, уведомления, отмена заявки.
- Карточка подтверждения перед отправкой в интерфейсе: сейчас явная просьба в тексте считается подтверждением.
- Другие типы отсутствий (отпуск, больничный, командировка). Новый тип добавляется записью в `buddy.request_types` и правилами в Go.
