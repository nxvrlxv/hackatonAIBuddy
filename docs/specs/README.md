# SDD-спецификации AI-buddy

Здесь описано, как ведёт себя агент AI-buddy и его инструменты. Спецификация отвечает на вопрос «что система должна делать», код отвечает «как», тесты подтверждают, что код делает то, что написано в спецификации.

## Как мы работаем со спецификациями

Подход близок к spec-kit: сначала спецификация сценария, потом код, потом тесты по критериям приёмки.

1. **Спецификация.** Для каждого сценария фиксируем цель пользователя, шаги агента, вызываемые инструменты с контрактом входа и выхода, права, ошибки и критерии приёмки.
2. **Код.** Инструмент или ручка реализуется строго по контракту. Права проверяет сервис по токену, а не промпт.
3. **Тесты.** Каждый критерий приёмки ссылается на тест, который его проверяет. Если критерий пока проверяется только вручную, это помечено.
4. **Изменения.** Спецификация правится в том же PR, что и код. Расхождение между спецификацией и кодом считается ошибкой.

## Формат файла

Каждая спецификация сценария содержит одинаковые разделы:

| Раздел | Что в нём |
|---|---|
| Цель | Какую задачу стажёра закрывает сценарий |
| Пользовательские истории | Что говорит стажёр и что получает |
| Поведение агента | Шаги, порядок вызова инструментов, правила ответа |
| Инструменты и контракты | Имя, сервер, вход, выход, ошибки |
| Права и данные | Откуда берётся пользователь, что ему доступно |
| Ошибки и граничные случаи | Что видит пользователь при сбое |
| Критерии приёмки | Проверяемые утверждения со ссылкой на тесты |
| Вне рамок | Что сознательно не делаем в прототипе |

## Сводная схема инструментов

| Инструмент | MCP-сервер | Сценарий | Меняет данные |
|---|---|---|---|
| `whoami` | `mcp-buddy` | 04, вызывается кодом агента в начале каждого хода | нет |
| `search_docs` | `mcp-buddy` | 01, вызывается кодом агента до модели на каждый вопрос; модель может вызвать повторно | нет |
| `team_members` | `mcp-buddy` | 04 | нет |
| `get_checklist` | `mcp-buddy` | 02 | при первом вызове создаёт стажёру задачи по шаблонам |
| `update_task_status` | `mcp-buddy` | 02 | да, статус своей задачи; `done` от стажёра сохраняется как `review` (на проверке у наставника) |
| `get_request_types` | `mcp-corporate` | 03 | нет |
| `list_my_requests` | `mcp-corporate` | 03 | нет |
| `create_time_off_request` | `mcp-corporate` | 03 | да, новая заявка |

Все инструменты получают пользователя только из Bearer-токена. Ни один инструмент не принимает `user_id` в аргументах.

Принять или отклонить задачу может только наставник кнопками в интерфейсе (REST `/api/reviews/...`). MCP-инструмента для этого нет, поэтому агент сделать это не может.

## Тестовые данные

Пользователи, команды, задачи, заявки и описания команд (`data/knowledge/team-*`) придуманы для прототипа. Общие документы базы знаний (`data/knowledge/common/`) взяты из открытого инженерного плейбука Авито как пример наполнения и не выдаются за действующие регламенты. Тестовые учётки перечислены в корневом [README](../../README.md#логины-для-демо).
