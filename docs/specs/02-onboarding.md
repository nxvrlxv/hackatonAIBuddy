# 02. Чек-лист адаптации, прогресс и следующий шаг

Код: `backend/internal/onboarding/` (`model.go`, `service.go`, `postgres.go`, `mcp.go`, `http.go`), миграция `backend/migrations/0006_onboarding.up.sql`, инструменты `get_checklist` и `update_task_status` в `agent/src/agent/graph.py`.
Тесты: `backend/internal/onboarding/*_test.go`.

## Цель

Стажёр видит этапы адаптации, статусы задач и следующий шаг. Он может спросить Buddy «что мне делать дальше?» и отметить выполненную задачу прямо в чате. Панель интерфейса и агент показывают одни и те же данные, потому что работают через один сервис.

## Пользовательские истории

- «Что мне делать дальше?» Buddy называет следующую невыполненную задачу и общий прогресс.
- «Я получил доступ к GitLab.» Buddy отмечает задачу «Доступ к GitLab» выполненной и называет новый прогресс.
- «Я начал настраивать VPN.» Задача переходит в статус «в работе».
- Наставник или руководитель спрашивает про чек-лист: список пустой, чек-лист есть только у стажёров.

## Модель данных

| Сущность | Таблица | Поля |
|---|---|---|
| Этап | `buddy.onboarding_stages` | `code`, `title`, `position` |
| Шаблон задачи | `buddy.task_templates` | `stage_id`, `team_id` (NULL для всех команд), `title`, `description`, `position` |
| Задача стажёра | `buddy.intern_tasks` | `user_id`, `template_id`, `status`, `completed_at` |

Статусы: `todo`, `in_progress`, `done`.

Тестовые этапы: «Знакомство с командой» (`team`), «Доступы и инструменты» (`tools`), «Первые задачи» (`first_tasks`). Десять общих задач и командные задачи для `travel`, `delivery`, `adverts`, `payments`. У Саши (`sasha.intern`) для демонстрации первый этап уже пройден, а GitLab в работе.

## Поведение

1. **Создание задач.** При первом обращении к чек-листу стажёру создаются задачи по общим шаблонам и шаблонам его команды. Повторный вызов ничего не дублирует. Для ролей `mentor` и `lead` задачи не создаются.
2. **Сборка чек-листа.** Задачи сортируются по позиции этапа и задачи. Для каждого этапа считаются `done` и `total`. Общий процент равен `done * 100 / total` с округлением вниз. `next` указывает на первую по порядку задачу со статусом не `done`; если всё пройдено, `next = null`.
3. **Смена статуса.** Меняется только своя задача. При переходе в `done` записывается `completed_at`; повторный `done` его не сдвигает. При переходе в другой статус `completed_at` очищается. В ответе возвращаются задача и пересчитанный общий прогресс.
4. **Агент.** На вопросы о шагах и прогрессе вызывает `get_checklist`. Когда стажёр сообщает о выполненной задаче, агент сразу вызывает `update_task_status` с частью названия задачи. Код агента сам находит `task_id` по названию; при нескольких совпадениях или отсутствии задачи возвращает модели список названий для уточнения. Агент не говорит «отмечено» без результата инструмента.

## Инструменты (MCP, сервер `mcp-buddy`)

### `get_checklist`

Вход: `{}`.
Выход:
```json
{
  "progress": { "done": 4, "total": 11, "percent": 36 },
  "next": { "id": 15, "title": "Доступ к GitLab", "description": "…", "status": "in_progress" },
  "stages": [
    { "code": "team", "title": "Знакомство с командой", "done": 4, "total": 4,
      "tasks": [ { "id": 11, "title": "Встреча с наставником", "description": "…", "status": "done",
                   "completed_at": "2026-11-10T09:00:00Z" } ] }
  ]
}
```

### `update_task_status`

Вход: `{ "task_id": 15, "status": "done" }`.
Выход: `{ "task": { … }, "progress": { "done": 5, "total": 11, "percent": 45 } }`.

Ошибки, понятные модели:
- «неверный статус: допустимы todo, in_progress, done»;
- «задача не найдена в чек-листе пользователя; возьми task_id из get_checklist»;
- «не удалось обновить задачу» при сбое базы (детали скрыты).

## REST для панели интерфейса

Все ручки за `requireAuth`, пользователь из токена.

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/checklist` | 200, тот же объект, что у `get_checklist` |
| PATCH | `/api/checklist/tasks/{id}` | тело `{"status":"done"}`; 200 `{task, progress}`; 400 неверный id, JSON или статус; 404 задача не найдена; 401 без токена |

## Права и данные

- `user_id` берётся только из токена. Запрос на чужую задачу возвращает «не найдена», а не «запрещено», чтобы не раскрывать существование чужих id.
- Роль проверяется в SQL: задачи создаются только пользователю с ролью `intern`.

## Критерии приёмки

| Критерий | Тест |
|---|---|
| Прогресс, этапы и `next` считаются правильно, `next = null` когда всё пройдено | `service_test.go::TestBuild` |
| Задачи создаются при первом запросе и не дублируются | `postgres_test.go::TestEnsureTasks`, `service_test.go::TestChecklist` |
| Меняется только своя задача, чужая даёт «не найдена» | `postgres_test.go::TestUpdateStatus` |
| Неверный статус отклоняется до обращения к базе | `postgres_test.go::TestStatusValid`, `service_test.go::TestSetStatus` |
| MCP-инструменты берут пользователя из токена и отдают понятные ошибки | `mcp_test.go::TestGetChecklistTool`, `mcp_test.go::TestUpdateTaskStatusTool` |
| REST-ручки отдают те же данные и коды ошибок | `http_test.go::TestGetChecklistHTTP`, `http_test.go::TestSetStatusHTTP` |
| Ручки фичи подключаются только за проверкой токена | `httpapi/routes_test.go::TestWithRoutesMountsBehindAuth` |
| Стажёр отмечает задачу фразой в чате, прогресс в ответе растёт | Вручную, сценарий 2 в [README](../../README.md#порядок-проверки) |

## Вне рамок

- Отдельные чек-листы для наставника и руководителя.
- Сроки задач, напоминания (ИИ-крон) и уведомления наставнику.
- Редактирование шаблонов через интерфейс: шаблоны задаются миграцией.
