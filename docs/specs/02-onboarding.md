# 02. Чек-лист адаптации, следующий шаг и проверка наставником

Код: `backend/internal/onboarding/` (`model.go`, `service.go`, `postgres.go`, `mcp.go`, `http.go`), миграции `0006_onboarding.up.sql` и `0008_task_review.up.sql`, инструменты `get_checklist` и `update_task_status` в `agent/src/agent/graph.py`.
Тесты: `backend/internal/onboarding/*_test.go`, `agent/tests/test_task_review.py`, `agent/tests/test_prefetch_guard.py`.
Общий контракт бэкенда, интерфейса и агента: [docs/approvals-contract.md](../approvals-contract.md).

## Цель

Стажёр видит этапы адаптации, статусы задач и следующий шаг. Он спрашивает Buddy «что мне делать дальше?» и сообщает о выполненной задаче прямо в чате или кнопкой на главной. Выполненной задачу делает только наставник: он принимает её или возвращает с комментарием. Главная, кабинет наставника и агент работают через один сервис, поэтому показывают одни и те же данные.

## Пользовательские истории

- Стажёр: «Что мне делать дальше?» Buddy называет следующую задачу и общий прогресс.
- Стажёр: «Как выполнить задачу «Настроить VPN»?» Buddy объясняет по описанию задачи и документам, статус не меняется.
- Стажёр: «Я получил доступ к GitLab.» Задача уходит наставнику на проверку, Buddy так и отвечает: «отправлена на проверку», а не «выполнена».
- Стажёр: «Я начал настраивать VPN.» Задача переходит в статус «в работе».
- Наставник видит на главной запросы на проверку от своих стажёров и принимает их или отклоняет с комментарием.
- Стажёр видит возвращённую задачу с плашкой «Нужно доработать» и комментарием, Buddy пересказывает комментарий.
- Наставник видит прогресс адаптации каждого своего стажёра.
- Руководитель спрашивает про чек-лист: чек-листа у него нет, он есть только у стажёров.

## Модель данных

| Сущность | Таблица | Поля |
|---|---|---|
| Этап | `buddy.onboarding_stages` | `code`, `title`, `position` |
| Шаблон задачи | `buddy.task_templates` | `stage_id`, `team_id` (NULL для всех команд), `title`, `description`, `position` |
| Задача стажёра | `buddy.intern_tasks` | `user_id`, `template_id`, `status`, `completed_at`, `submitted_at`, `reviewed_by`, `reviewed_at`, `review_comment` |
| Наставник стажёра | `buddy.users.mentor_id` | |

## Статусы задачи

| Статус | Кто ставит | Смысл | Входит в прогресс |
|---|---|---|---|
| `todo` | система | не начата | нет |
| `in_progress` | стажёр; бэкенд при отклонении | в работе или нужно доработать | нет |
| `review` | стажёр (его запрос `done` сохраняется как `review`) | отправлена наставнику | нет |
| `done` | только наставник (принять) | принята | да |

```
todo ──▶ in_progress ──▶ review ──принять──▶ done
  └──────────────────────▲  │
                            └──отклонить с комментарием──▶ in_progress
```

Тестовые этапы: «Знакомство с командой» (`team`), «Доступы и инструменты» (`tools`), «Первые задачи» (`first_tasks`). Десять общих задач и командные задачи для `travel`, `delivery`, `adverts`, `payments`.

Демо-состояние у Саши (`sasha.intern`):
- первый этап пройден;
- «Доступ к GitLab» в работе;
- «Доступ к Jira» на проверке у `anna_mentor`.

## Поведение

1. **Создание задач.** При первом обращении к чек-листу стажёру создаются задачи по общим шаблонам и шаблонам его команды. Повторный вызов ничего не дублирует. Для ролей `mentor` и `lead` задачи не создаются.
2. **Сборка чек-листа.**
   - Задачи сортируются по позиции этапа и задачи.
   - Для каждого этапа считаются `done` и `total`. Общий процент равен `done * 100 / total` с округлением вниз.
   - `next` указывает на первую по порядку задачу в статусе `todo` или `in_progress`: задачи на проверке пропускаются. Если открытых задач нет, `next = null`.
3. **Действие стажёра.**
   - Меняется только своя задача.
   - Запрос `done` сохраняется как `review` с отметкой `submitted_at`, комментарий прошлого отклонения очищается.
   - Повторная отправка задачи, которая уже на проверке, ничего не меняет, `submitted_at` прежний: очередь у наставника не перемешивается.
   - Принятую задачу менять нельзя.
   - В ответе фактический статус и пересчитанный прогресс.
4. **Действие наставника.**
   - Принять: `review` → `done`, записываются `completed_at`, `reviewed_by` и `reviewed_at`.
   - Отклонить: `review` → `in_progress` с обязательным комментарием от 1 до 500 символов после обрезки пробелов.
   - Наставник работает только с задачами стажёров, у которых `mentor_id` равен его id. Чужая задача выглядит как несуществующая.
5. **Очередь проверки.** Задачи на проверке у стажёров наставника, старые сверху.
6. **Прогресс стажёров.** Для каждого стажёра наставника: `done`, `total`, `percent`, число задач на проверке и название текущего этапа (пустое, если всё принято).
7. **Агент.**
   - На вопросы о шагах, прогрессе и проверке вызывает `get_checklist`.
   - На вопрос «как выполнить задачу «…»» код агента сам добавляет описание задачи из чек-листа в контекст модели, статус не меняется.
   - `update_task_status` вызывается, когда стажёр сообщает, что уже сделал или начал задачу. Код агента сам находит задачу по части названия. Если совпадений несколько, выбирает единственную ещё не отправленную; иначе возвращает модели список названий для уточнения.
   - Код агента, а не модель, проверяет, что в сообщении пользователя действительно есть сообщение о выполнении («сделал», «получил», «настроил»…), а не вопрос «как». Иначе статус не меняется.
   - Задачу на проверке или принятую код не отправляет повторно.
   - Если модель написала «отправил на проверку», но `update_task_status` не прошёл, код один раз просит модель исправиться. При повторной ошибке заменяет ответ честной поправкой.
   - Принять или отклонить задачу через чат нельзя.

## Инструменты (MCP, сервер `mcp-buddy`)

### `get_checklist`

Вход: `{}`.
Выход:
```json
{
  "progress": { "done": 4, "total": 11, "percent": 36 },
  "next": { "id": 15, "title": "Доступ к GitLab", "description": "…", "status": "in_progress" },
  "stages": [
    { "code": "tools", "title": "Доступы и инструменты", "done": 0, "total": 4,
      "tasks": [
        { "id": 15, "title": "Доступ к GitLab", "description": "…", "status": "in_progress" },
        { "id": 16, "title": "Доступ к Jira", "description": "…", "status": "review",
          "submitted_at": "2026-11-15T10:12:00Z" }
      ] }
  ]
}
```

`submitted_at` есть, пока задача на проверке. `review_comment` есть у задачи, которую вернули на доработку.

### `update_task_status`

Вход: `{ "task_id": 15, "status": "done" }`. Для стажёра `done` означает «отправить наставнику на проверку».
Выход: `{ "task": { …, "status": "review" }, "progress": { "done": 4, "total": 11, "percent": 36 } }`.

Ошибки начинаются с короткого машинного кода, который агент пересказывает без догадок:
- `task not found: …` — задачи нет в чек-листе пользователя;
- `task already approved: …` — задача уже принята наставником;
- неверный статус и сбой базы (детали скрыты).

## REST для интерфейса

Все ручки за `requireAuth`, пользователь и роль из токена.

**Стажёр**

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/checklist` | 200, тот же объект, что у `get_checklist` |
| PATCH | `/api/checklist/tasks/{id}` | тело `{"status":"todo\|in_progress\|review\|done"}`; 200 `{task, progress}`; 400 неверный id, JSON или статус; 404 задача не найдена; 409 `task already approved` |

**Наставник** (ручки только для роли `mentor`, остальным 403 `forbidden`)

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/reviews` | 200 `{reviews: [{task_id, task_title, task_description, stage_title, intern: {id, full_name}, submitted_at}]}` |
| POST | `/api/reviews/{task_id}/approve` | 200 `{task_id, status: "done"}` |
| POST | `/api/reviews/{task_id}/reject` | тело `{"comment":"…"}`; 200 `{task_id, status: "in_progress"}`; 422 `comment is required` |
| GET | `/api/interns` | 200 `{interns: [{id, full_name, done, total, percent, in_review, stage}]}` |

Ошибки принятия и отклонения: 400 `invalid task id`; 404 `not found` (задачи нет или стажёр не свой); 409 `task is not in review`.

## Права и данные

- `user_id` и роль берутся только из токена. Запрос на чужую задачу возвращает «не найдена», а не «запрещено», чтобы не раскрывать существование чужих id.
- Задачи создаются только пользователю с ролью `intern`, это проверяется в SQL.
- Ручки проверки сначала проверяют роль `mentor` (403), затем SQL-условие `mentor_id = id наставника`. Даже с ролью наставника чужую задачу принять нельзя.
- Поставить `done` может только наставник. Ни запрос стажёра, ни агент сделать это не могут.

## Критерии приёмки

| Критерий | Тест |
|---|---|
| Прогресс, этапы и `next` считаются правильно; задачи на проверке пропускаются; `next = null`, когда открытых задач нет | `service_test.go::TestBuild` |
| Задачи создаются при первом запросе и не дублируются | `postgres_test.go::TestEnsureTasks`, `service_test.go::TestChecklist` |
| Меняется только своя задача, чужая даёт «не найдена» | `postgres_test.go::TestUpdateStatus` |
| `done` от стажёра становится `review` и получает `submitted_at`, принятую задачу менять нельзя | `service_test.go::TestSetStatus`, `postgres_test.go::TestUpdateStatus` |
| Повторная отправка не сдвигает `submitted_at` | условие в SQL `postgres.go::UpdateStatus`; модульные тесты с `pgxmock` проверяют запрос, но не его результат, поэтому вручную на стенде |
| Неверный статус отклоняется до обращения к базе | `postgres_test.go::TestStatusValid`, `service_test.go::TestSetStatus` |
| Очередь проверки только по своим стажёрам, старые сверху | `service_test.go::TestReviews`, `postgres_test.go::TestListReviews` |
| Принять и отклонить можно только задачу своего стажёра на проверке; комментарий обязателен и не длиннее 500 символов | `service_test.go::TestApprove`, `service_test.go::TestReject`, `postgres_test.go::TestApproveReject` |
| Прогресс стажёров наставника | `service_test.go::TestInterns`, `postgres_test.go::TestListInterns` |
| MCP-инструменты берут пользователя из токена и отдают понятные ошибки | `mcp_test.go::TestGetChecklistTool`, `mcp_test.go::TestUpdateTaskStatusTool` |
| REST-ручки отдают те же данные и коды; ручки наставника дают 403 другим ролям | `http_test.go::TestGetChecklistHTTP`, `TestSetStatusHTTP`, `TestListReviewsHTTP`, `TestReviewActionsHTTP`, `TestListInternsHTTP` |
| Ручки фичи подключаются только за проверкой токена | `httpapi/routes_test.go::TestWithRoutesMountsBehindAuth` |
| Вопрос «как выполнить задачу» не отправляет её на проверку, описание задачи подставляет код | `test_prefetch_guard.py::test_how_to_question_does_not_submit_task`, `test_quoted_task_description_is_added_by_code` |
| Ложное «отправил» без вызова инструмента исправляется: один повтор, затем честная поправка | `test_task_review.py::test_false_claim_gets_one_retry_and_tool_is_called`, `test_false_claim_twice_becomes_honest_text` |
| Задача на проверке или принятая не отправляется повторно; из нескольких совпадений выбирается единственная открытая | `test_task_review.py::test_task_in_review_or_done_is_not_resubmitted`, `test_resolver_prefers_the_only_open_match` |
| Полный путь «стажёр отправил → наставник принял или отклонил → стажёр видит результат» | Вручную, сценарий 2 в [README](../../README.md#порядок-проверки) |

## Вне рамок

- Уведомления наставнику: запрос просто появляется у него на главной.
- Сроки задач и напоминания (ИИ-крон).
- Редактирование шаблонов через интерфейс: шаблоны задаются миграцией.
