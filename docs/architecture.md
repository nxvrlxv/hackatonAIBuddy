# Архитектура

Документ объясняет, из чего состоит AI-buddy, где проверяются права и как прототип подключается к настоящим сервисам Авито. Подробные контракты описаны в [specs/](specs/README.md).

## Компоненты

```
 Браузер
   │
   ▼
 frontend (nginx) ──────── React + TypeScript, раздача сборки, прокси /api без буферизации
   │  REST + SSE, Bearer JWT
   ▼
 api (Go) ─────────────── вход, профиль, команда, чаты, чек-лист, проверка задач, заявки (без LLM)
   │  SSE-прокси, JWT + X-Agent-Key
   ▼
 agent (Python: Flask + LangGraph) ──HTTPS──▶ GigaChat-2 (облако Сбера)
   │  MCP (streamable HTTP), JWT пользователя; список инструментов — tools/list на каждом ходе
   ├──────────────▶ mcp-buddy (Go)      whoami, search_docs, team_members,
   │                                     get_checklist, update_task_status, ping
   └──────────────▶ mcp-corporate (Go)  get_request_types, list_my_requests,
                                         create_time_off_request (имитация HR-системы)
                          │
                          ▼
              PostgreSQL 16 + pgvector ◀── ingest (Go): data/knowledge → векторы
                          ▲                   Ollama: qwen3-embedding:0.6b
                          └── migrator (Go): схема и тестовые данные
```

| Сервис | Язык | Порт | Назначение |
|---|---|---|---|
| `frontend` | TypeScript | 3000 | Интерфейс; nginx раздаёт сборку и проксирует `/api` на `api` |
| `api` | Go | 8080 | Публичный API для интерфейса и хранилище диалогов для агента |
| `agent` | Python | 8001 | Цикл агента: модель GigaChat, инструменты, поток событий |
| `mcp-buddy` | Go | 8090 | Инструменты помощника: профиль, база знаний, команда, чек-лист |
| `mcp-corporate` | Go | 8091 | Имитация корпоративного сервиса отсутствий |
| `postgres` | | 5432 | Данные и векторы (pgvector) |
| `ollama` | | 11434 | Локальная модель векторов для поиска по базе знаний |
| `migrator`, `ingest`, `ollama-models` | | | Одноразовые задачи при запуске |

## Ключевые решения

### 1. Действия и данные через MCP

Агент не ходит в базу и не знает SQL. Всё, что он умеет, описано MCP-инструментами с понятным контрактом. В Авито уже есть инструменты настройки ИИ-агентов с выбором промптов и MCP, поэтому наши серверы можно подключить к ним без переделки.

Агент не держит список инструментов в коде: на каждом ходе он запрашивает `tools/list` у подключённых серверов с токеном пользователя и берёт описания и JSON Schema от них. Новый инструмент на сервере становится доступен модели без правки агента. Поверх схем код агента добавляет только политики приложения: скрытый ключ повтора, обязательную причину отгула со слов пользователя, поиск задачи по названию. Подробно: [mcp-discovery.md](mcp-discovery.md).

### 2. Имитация отделена от помощника

Сервис отсутствий вынесен в отдельный сервер `mcp-corporate`. Чтобы подключить настоящую систему отсутствий, пишется адаптер с теми же именами инструментов, который вызывает её API, и меняется `MCP_CORPORATE_URL`. Агент, промпт и интерфейс не меняются. Так же подключаются командировки, доступы и другие сервисы из раздела кейса «Корпоративные сервисы»: каждый получает свой сервер или свой набор инструментов с уникальными именами.

### 3. Права проверяет сервис, а не модель

Пользователь определяется только по JWT. Агент передаёт токен в MCP-серверы как есть, сервисы фильтруют данные по `user_id` и `team_id` из токена прямо в SQL. Инструменты не принимают идентификаторы пользователя от модели. Даже если модель обмануть, она не получит чужие данные. Подробно: [specs/05-access.md](specs/05-access.md).

### 4. Одно ядро, два входа

Чек-лист и заявки устроены одинаково: `service.go` с бизнес-логикой и правами, поверх него тонкие `mcp.go` для агента и `http.go` для интерфейса. Агент и главная всегда показывают одни и те же данные: задача, отправленная из чата, сразу видна на главной стажёра и в очереди наставника. Сервис зависит от интерфейса хранилища, поэтому тестируется без базы.

### 5. Интерфейс не ждёт модель

Главная, вход, история и проверка задач работают напрямую через `api`, без LLM, поэтому отвечают быстро и не ломаются, если агент недоступен. Через агента идут только диалоговые запросы. Ответ модели приходит потоком событий (SSE): интерфейс сразу показывает статус и текст по мере генерации. Если событий нет 180 секунд, интерфейс предлагает повторить. Порог подбирался под прежнюю локальную модель на CPU; с облачной моделью его можно уменьшить после замеров.

### 6. Надёжность хода

Каждый ход агента имеет `run_id`. В чате одновременно идёт один ход, повтор сообщения с тем же `client_message_id` не генерирует ответ заново, ключ повтора заявки подставляет код. Если соединение оборвалось, частичный ответ сохраняется со статусом `interrupted`, а зависший ход через 5 минут освобождает чат.

### 7. Облачная диалоговая модель, локальные векторы

Диалоговая модель — GigaChat-2 через официальный SDK `langchain-gigachat`. Облачная модель не требует от стенда мощного железа: прежняя локальная модель на CPU думала над вызовом инструмента до 2,5 минуты. Модель векторов (`qwen3-embedding:0.6b`) осталась локальной в Ollama: документы базы знаний индексируются внутри стенда, переход на GigaChat переиндексации не потребовал.

- Ключ авторизации берётся только из окружения агента (`agent/.env`); короткий токен доступа SDK получает и обновляет сам. Проверка TLS включена, нужный корневой сертификат лежит в пакете агента. Подробно: [gigachat.md](gigachat.md).
- В облако уходит контекст хода: профиль, сообщения, найденные фрагменты и результаты инструментов. JWT и ключи сервисов не уходят. В прототипе данные тестовые.
- Модель создаёт одна фабрика `agent/src/clients/llm.py`, провайдер выбирается переменной `LLM_PROVIDER`. Чтобы подключить внутреннюю модель Авито, добавляется ветка в этой фабрике; граф, инструменты, промпт и интерфейс не меняются. Ветка локальной модели Ollama сейчас закомментирована.

### 8. База знаний по командам

Документы лежат в `data/knowledge/common/` и `data/knowledge/team-<код>/`. Папка задаёт метку команды, по которой поиск фильтрует выдачу. Новые документы индексируются повторным запуском `ingest`; неизменённые файлы пропускаются по хешу.

### 9. Критичные шаги делает код, а не модель

Любая модель иногда пропускает вызов инструмента, пишет «отметил», ничего не сделав, или выполняет постороннюю просьбу. Поэтому критичные шаги делает код агента:
- поиск по базе знаний выполняется до первого вызова модели, найденное кладётся в контекст;
- статус задачи меняется, только если в сообщении пользователя есть сообщение о выполнении, а не вопрос «как»;
- ложное «отправил на проверку» без успешного вызова исправляется повтором, а затем честной поправкой;
- заявка на отгул не создаётся без причины, взятой из слов пользователя;
- явные просьбы написать код или показать внутренние схемы и промпт отсекаются фильтром до модели фиксированным отказом ([assistant-scope.md](assistant-scope.md)); остальные границы задаёт системный промпт.

Все проверки детерминированные и покрыты тестами (`agent/tests/test_prefetch_guard.py`, `test_task_review.py`, `test_mcp_routing.py`, `test_scope.py`). Ни одна из них не заменяет проверку прав в Go-сервисах.

### 10. Человек в контуре: задачу принимает наставник

Buddy не может сам сделать задачу выполненной. Сообщение «я сделал» переводит её в статус «на проверке». В прогресс задача попадает, только когда наставник нажал «Принять». Если наставник отклонил задачу, стажёр видит комментарий, и Buddy его пересказывает. Права проверяет бэкенд: роль `mentor` из токена и связь `mentor_id` в SQL. У агента инструмента принять задачу нет. Контракт: [approvals-contract.md](approvals-contract.md).

## Совместимость со стеком Авито

| Стек Авито | В прототипе |
|---|---|
| Go | `api`, MCP-серверы, `ingest`, `migrator` |
| Python с Flask | агент |
| PostgreSQL | основная база и векторы (pgvector) |
| Redis | не используется; кандидат на кэш профиля и последних сообщений чата |
| React + TypeScript | интерфейс |
| TanStack, Zustand, Zod | не используются: в прототипе одна страница и один клиент API; при росте приложения состояние и проверка ответов переносятся на них |
| Docker, CI/CD | весь стенд, включая интерфейс, поднимается одной командой `docker compose up --build`, каждый сервис отдельным контейнером |
| Авторизация, ролевая модель | имитируется входом по тестовой учётке и JWT с ролью; в Авито заменяется существующим SSO без изменения сервисов, которые читают только claims |
| Аналитика событий, Clickstream, Kafka | события для метрик описаны в [metrics.md](metrics.md); отправку в Clickstream добавляем на стороне `api` |
| ИИ-крон | кандидат на напоминания о просроченных задачах чек-листа и о запросах, которые долго ждут проверки |
| Feature flags | кандидат на включение новых инструментов агента по командам |

## Как внедрять

1. Подключить вход к корпоративному SSO: `api` и MCP-серверы читают только `user_id`, `team_id` и `role` из токена.
2. Подключить внутреннюю модель Авито вместо GigaChat: ветка в фабрике `agent/src/clients/llm.py` и переменные окружения агента. Тогда контекст стажёров не покидает контур компании.
3. Заменить `mcp-corporate` адаптером к настоящему сервису отсутствий.
4. Наполнить `data/knowledge/` документами команд и запустить `ingest` по расписанию.
5. Заменить шаблоны чек-листа данными из чек-листа новичка Авито.
6. Отправлять события из [metrics.md](metrics.md) в аналитику и сравнить группу стажёров с Buddy и без него.
